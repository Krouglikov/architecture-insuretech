# Список проблем и рисков

```markdown
Сервисы core-app и ins-comp-settlement получают данные о доступных продуктах через REST API сервиса
ins-product-aggregator. В момент вызова он:

* запрашивает информацию из всех страховых компаний (сейчас их пять),
* агрегирует её в единый список,
* возвращает этот список в рамках того же синхронного запроса.

Чтобы ускорить работу сервисов, при изначальном проектировании команда решила хранить локальные реплики данных о
продуктах и тарифах в сервисах core-app и ins-comp-settlement.

Сервис core-app осуществляет запрос к ins-product-aggregator раз в 15 минут, а ins-comp-settlement — раз в сутки
(ночью), при формировании реестра оформленных страховок. Иногда команда сталкивается с ошибками взаимодействия между
этими сервисами. Они связаны с задержками ответов или ошибками при взаимодействии с API страховых компаний.

Дополнительно сервис ins-comp-settlement раз в сутки осуществляет запрос в core-app по REST API для получения всех
оформленных за день страховок. Эти данные он использует.

В ближайшее время InsureTech планирует подписать агентское соглашение ещё с пятью страховыми компаниями. Вам предстоит
спроектировать решение, которое устранит текущие проблемы.
```

## Текущие проблемы

1. Синхронная агрегация данных в реальном времени  
   Сервис `ins-product-aggregator` при каждом запросе синхронно опрашивает все страховые компании. При увеличении их
   количества это приведёт к повышенному риску таймаутов и снижению скорости выполнения запроса, особенно если одна из
   компаний отвечает долго или вообще недоступна.

2. Рассинхронизация данных в локальных репликах  
   Из-за разницы в частоте обновления данных в сервисах `core-app` (раз в 15 минут) и `ins-comp-settlement` (раз в
   сутки) могут возникать расхождения в данных между локальными репликами. Насколько это расхождение критично, нужно
   изучить отдельно.

3. REST-зависимости между внутренними сервисами  
   Взаимодействие по REST API создаёт:
    - Жёсткую связанность между сервисами.
    - Риск недоступности данных при временных сбоях.

---

## Риски при росте нагрузки

| Риск                                                          | Последствия                                               | Вероятность | Критичность                  |
|---------------------------------------------------------------|-----------------------------------------------------------|-------------|------------------------------|
| Увеличение времени ответа `ins-product-aggregator`            | Превышение таймаутов в `core-app` и `ins-comp-settlement` | Высокая     | Низкая                       |
| Частые сбои при взаимодействии с новыми страховыми компаниями | Простои в оформлении страховок                            | Средняя     | Высокая                      |
| Расхождение данных между сервисами                            | Ошибки в расчётах и выплатах                              | Высокая     | Неясна, потенциально высокая |

---

## Вывод

Текущая архитектура при увеличении числа партнеров может привети у деградации работы всего приложения.

Желательно перейти от синхронной агрегации к асинхронной, для чего использовать брокер сообщений, и event-driven
архитектуру.
